# vertical-research

**산업별(버티컬) 영업 대상 업체를 AI 에이전트들이 나눠 조사하고, 스크립트로 채점해, 한국어 보고서로 정리하는 Claude Code 플러그인입니다.**

엔진·SDK 같은 B2B 제품을 받아 **자기 제품에 넣어 개발해 줄 파트너사**를 찾는 영업 리서치에 맞춰 만들었습니다. `"건설현장 출입통제"`처럼 버티컬 하나를 넣으면 다음을 만들어 줍니다.

- 그 시장의 경쟁사와 우리 제품의 차별점
- 우리 SDK 를 탑재할 수 있는 후보 업체 순위 (항목별 점수와 출처 링크 포함)
- 영업 담당자가 바로 읽을 수 있는 한국어 보고서
- 여러 버티컬을 돌릴수록 쌓이는 전체 업체 명부 (업체 1곳 = 제안서 1건)

## 빠른 시작

```
/plugin marketplace add MMSS9402/vertical-research
/plugin install vertical-research@vertical-research
```

새 세션을 연 뒤, 조사 결과를 둘 폴더에서 실행합니다.

```
/vertical-research:init                                   # 설정 파일 만들기 (폴더당 한 번)
/vertical-research:run "건설현장 출입통제"                  # 설정의 기본 지역·후보 수로 조사
/vertical-research:run "무인매장 신원확인" 북미 20           # 북미(미국·캐나다·멕시코)에서 20곳
/vertical-research:run "스마트빌딩 방문객 관리" 북미,남미 30  # 두 대륙을 함께
```

| 입력 | 의미 | 생략하면 |
|---|---|---|
| 첫 번째 (따옴표) | 조사할 버티컬 | 생략할 수 없음 |
| 두 번째 | 조사 지역. 대륙 이름(`북미`, `남미`)이나 국가 이름(`Korea` 등) | 설정의 `regions` |
| 마지막 숫자 | 최종 후보 수 | 설정의 `top_n` |

처음에는 후보 수를 10 정도로 작게 잡아 시험해 보세요. 한 번 실행에 수십 분이 걸리고 토큰을 많이 씁니다.

## 어떤 업체를 찾나요?

**우리 엔진을 받아 자기 제품에 넣어 개발할 수 있는 곳**을 찾습니다. 꼭 SI 업체일 필요는 없지만, SW·HW 를 직접 개발해 외부 고객에게 파는 사업이 있어야 합니다. 예시 설정 기준으로는 아래 세 가지가 모두 맞아야 합니다.

1. **외부 엔진을 올릴 자체 HW 가 있다** — IP·AI 카메라, AI Box·엣지 분석 장비, 출입 단말기, 키오스크, 게이트
2. **얼굴인식 제품·기능을 실제로 판다** — AI·Vision 일반(객체 검출, 번호판 인식 등)만 하는 곳은 아님
3. **Matching 까지 되는 자체 얼굴 엔진이 없다** — 타사 엔진을 쓰거나 얼굴 Detection 만 자체 보유한 곳은 대상

| 대상 (Target) | 대상 아님 |
|---|---|
| 카메라·AI Box 제조사 (타사 FR 엔진 탑재) | **VMS·보안 SW·SaaS 만 하는 업체** (엔진을 올릴 자체 HW 없음) |
| 출입·근태 단말기, 게이트, 키오스크 제조사 | **Matching 까지 되는 자체 얼굴 엔진**을 쓰는 업체, 얼굴인식 엔진·솔루션을 파는 경쟁사 |
| 이런 장비를 직접 개발하는 SI·솔루션사 | **얼굴인식 기능이 없는** AI·Vision 업체 |
| | 통신사, 유통·편의점, 은행, 호텔 운영사처럼 **솔루션을 사서 쓰는 최종 이용 기업** |
| | 자체 제품 없이 남의 제품만 파는 유통사, 활동을 확인할 수 없는 곳 |

엔진 출처(자체인지 타사인지)는 AI 가 홈페이지·데이터시트·보도자료·NIST FRTE 참가 목록 같은 공개 자료로 먼저 확인합니다. 공개 자료로 판단하지 못하면 제외하지 않고 `KO 미확정` 표시를 붙여 사람에게 넘깁니다.

최종 이용 기업은 버리지 않고 **단서로 씁니다.** 예를 들어 편의점 무인매장을 보면 그 매장의 키오스크와 솔루션을 납품한 업체를, 통신사를 보면 계열 IT 서비스사나 납품 SI 를 찾아 대신 조사합니다.

"대상 아님" 기준은 설정의 `knockout` 항목으로 정합니다. 걸린 업체는 순위에서 빠지고 제외 사유가 남습니다.

## 조사 지역

설정의 `region_groups` 에 대륙 이름과 국가 목록을 적어 두면, 실행할 때 대륙 이름만 넣으면 됩니다. 예시 설정의 기본값은 다음과 같습니다.

| 이름 | 국가 |
|---|---|
| `북미` | 미국, 캐나다, 멕시코 |
| `남미` | 아르헨티나, 볼리비아, 브라질, 칠레, 콜롬비아, 에콰도르, 가이아나, 페루, 파라과이, 수리남, 우루과이, 베네수엘라 |

- 조사 계획은 시장이 큰 나라(미국, 브라질 등)를 따로 떼고, 나머지 나라는 묶어서 나눕니다.
- 비영어권 나라는 포르투갈어·스페인어 일반 산업 용어(`reconhecimento facial`, `control de acceso` 등)로도 검색합니다.
- 본사가 지역 밖이어도 그 지역 법인이 사업을 하면 후보로 남깁니다. 이런 업체는 검사 단계에서 **지역 밖 업체 경고**로 따로 알려 주니, 넣을지 사람이 판단하면 됩니다.
- 중미·카리브처럼 목록에 없는 지역이 필요하면 설정에 이름과 국가 코드를 추가합니다.

## 동작 방식

역할을 나눈 에이전트 다섯 개가 순서대로 일하고, 단계 사이마다 **검사 스크립트**가 결과를 막거나 통과시킵니다.

```
① 계획        planner      조사 범위를 3~6개 단위로 나눕니다 (경쟁사 분석 + 후보 발굴)
② 조사        researcher   단위마다 동시에 웹을 조사합니다
   ✔ 검사                  빠진 항목, 출처 없는 근거가 있으면 되돌려 보냅니다
③ 검증        verifier     출처를 다시 열어 조사 내용을 따로 확인합니다
④ 채점        (스크립트)    제외 기준 적용, 점수 합산, 순위, 업체 명부 갱신
⑤ 작성        writer       한국어 보고서를 씁니다
⑥ 한국어 심사  ko-reviewer  번역투, 비문, AI 말투를 찾아냅니다
   ✔ 검사                  심각한 문제가 남으면 ⑤로 돌아갑니다 (최대 2회)
```

| 에이전트 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **planner** | 조사 단위, 핵심 질문, 검색어, 참고 출처를 정합니다 | 업체를 직접 조사하지 않습니다 |
| **researcher** | 업체 홈페이지와 공개 자료에서 항목별 근거를 모읍니다 | 확인하지 못한 내용을 추측으로 채우지 않습니다 |
| **verifier** | 출처를 직접 열어 근거와 제외 판정을 다시 봅니다 | 조사자의 메모를 보지 않습니다 (선입견 방지) |
| **writer** | 조사 결과를 영업용 보고서로 정리합니다 | 새 사실을 더하거나 점수를 바꾸지 않습니다 |
| **ko-reviewer** | 어색한 한국어를 심각도(S1~S3)별로 지적합니다 | 글을 직접 고치지 않습니다 |

**이렇게 만든 이유**

- **점수는 스크립트가 계산합니다.** AI 는 항목마다 상·중·하·확인불가와 근거만 냅니다.
- **모르면 "확인불가"입니다.** 0점으로 처리하고, 2개 이상이면 `근거부족` 표시를 붙입니다.
- **쓴 쪽과 검사하는 쪽이 다릅니다.** 자기 결과를 스스로 채점하면 관대해지기 쉽기 때문입니다.
- **사람은 표시된 업체만 다시 보면 됩니다.** 순위 경계, 근거 부족, 미검증 업체에 표시가 붙습니다.

병렬 조사 구조는 Anthropic 의 `deep-research` 예제 스킬을, 역할 분리와 스크립트 검사는 [iterate-solo](https://github.com/MMSS9402/iterate-solo)를 참고했습니다.

## 여러 버티컬을 돌릴 때

SI 업체 한 곳이 건설현장 근태, 스마트빌딩 출입통제, 공장 보안을 함께 하는 일이 흔합니다. 버티컬마다 따로 조사하면 같은 업체에 제안서가 두 번 가거나, 다른 사업부 실적이 근거로 섞입니다. 그래서 다음 규칙을 둡니다.

| 규칙 | 설명 |
|---|---|
| **업체 1곳 = 제안서 1건** | 여러 버티컬에서 나온 업체는 하나로 묶습니다. 점수가 가장 높은 버티컬이 **제안 버티컬**이고, 나머지는 같은 제안서의 확장 제안으로 들어갑니다 |
| **회사 공통 항목과 버티컬 항목** | 매출·임직원 수처럼 회사에 하나뿐인 값은 한 번 확인해 다시 씁니다. 자체 플랫폼·고객 사례처럼 사업부마다 다른 값은 버티컬마다 봅니다 |
| **근거는 해당 사업부 것만** | 건설 버티컬 점수에 스마트빌딩 사업부의 고객 사례를 쓰지 않습니다 |
| **제외 기준은 회사 단위** | 한 사업부라도 얼굴인식 엔진을 팔면 경쟁사로 보고 모든 버티컬에서 뺍니다 |
| **전체 업체 명부** | 실행할 때마다 `research/_registry/` 명부가 다시 만들어집니다. 팀 목표(예: 40곳)는 이 명부로 셉니다 |

새 버티컬을 채점하면 이전 실행들의 `candidates.csv`·`evidence.md` 도 새 명부 기준으로 자동 갱신됩니다. `report.md` 는 그대로이므로, 제안 버티컬이 바뀐 업체가 생기면 해당 보고서를 다시 써야 합니다.

## 결과물

실행마다 `research/<버티컬>-<날짜>/` 폴더가 생깁니다 (예: `research/건설·산업현장-출입통제-출역관리-20261021/`). 같은 버티컬을 다시 돌리면 `-2`, `-3` 폴더가 새로 생기고, 명부에는 가장 최근 실행만 반영됩니다. 명부에서 빼고 싶은 실행은 `research/_보관/` 처럼 `_` 로 시작하는 하위 폴더로 옮깁니다.

| 파일 | 내용 |
|---|---|
| `report.md` | **한국어 보고서.** 요약, 경쟁 구도, 후보 순위, 업체별 제안 포인트, 여러 버티컬에 걸친 업체, 다시 볼 업체 |
| `candidates.csv` | 순위, 항목별 등급과 점수, 검토 표시, 제안 버티컬, 제외 사유 (Excel 에서 바로 열립니다) |
| `evidence.md` | 업체별 항목 근거, 근거 사업부, 출처 링크 |
| `plan.md`, `notes/`, `records/`, `verify/` | 단계별 중간 결과 |
| `run.json` | 버티컬, 조사 지역, 대륙 지역이면 국가 목록 |
| `ko_review.json`, `run_log.md` | 한국어 심사 결과, 실행 기록 |

전체 업체 명부 `research/_registry/`:

| 파일 | 내용 |
|---|---|
| `companies.csv` | 업체 1곳 = 1줄. 제안 버티컬, 점수, 함께 제안할 버티컬, 제외 여부 |
| `summary.md` | 전체 업체 수, 제안 대상 수, 여러 버티컬에 걸친 업체 목록 |
| `company_facts.json` | 이미 확인한 회사 공통 정보 (다음 조사에서 다시 씁니다) |

### 검토 표시

| 표시 | 뜻 | 할 일 |
|---|---|---|
| `근거부족` | 확인하지 못한 항목이 2개 이상 | 빠진 정보를 직접 확인 |
| `경계` | 순위가 최종 후보 기준선 ±5위 안 | 넣을지 사람이 판단 |
| `미검증` | 검증 단계를 거치지 않음 | 출처를 직접 확인 |
| `타버티컬제안` | 다른 버티컬 점수가 더 높음 | 그 버티컬 기준으로 제안서 1건만 작성 |
| `타버티컬KO` | 다른 버티컬 조사에서 제외 기준에 걸림 | 제안 대상에서 제외 |
| `KO 판정 변경` | 예전 실행에서 걸렸던 제외 기준이 풀림 | 판정이 맞는지 확인 |
| `회사공통 불일치` | 매출 등 회사 공통 값이 조사마다 다름 | 어느 값이 맞는지 확인 |

## 설정 파일

`/vertical-research:init` 이 만들어 주며, 직접 쓸 때는 [`examples/vertical-research.config.md`](examples/vertical-research.config.md)를 복사해 고칩니다. 사람이 읽는 제품 요약과 스크립트가 읽는 `json vr-config` 블록으로 이루어집니다.

| 항목 | 의미 |
|---|---|
| `product_name`, `product_spec` | 제안할 제품 이름, 제품 사양 문서 경로 |
| `top_n`, `regions`, `output_dir` | 최종 후보 수, 기본 조사 지역, 결과 폴더 |
| `region_groups` | 대륙 이름 → 국가 코드 목록 (예: `"북미": ["US", "CA", "MX"]`) |
| `knockout` | 제외 기준. 예시: 직접 경쟁사, 단순 유통사, 관련 사업 없음, 활동 확인 불가, SDK 개발 주체 아님, **자체 Matching 엔진 보유, FR 제품·기능 없음, 외부 엔진 탑재 제품 없음** |
| `scoring` | 평가 항목과 배점. 항목마다 `scope` 를 `company`(회사 공통) 또는 `vertical`(버티컬별)로 지정 |
| `contact_roles` | 접촉할 담당자 직책의 우선순위 |
| `public_terms` | 웹 검색어에 써도 되는 공개 용어 |
| `confidential` | 절대 외부로 보내면 안 되는 내용 |

설정 끝에 `### ROLE_PLANNER`, `### ROLE_RESEARCHER`, `### ROLE_WRITER` 절을 두면 해당 에이전트에 팀 고유의 지침을 더할 수 있습니다.

> ⚠️ **설정 파일과 제품 사양 문서에는 사내 정보가 들어갑니다. 공개 저장소에 올리지 마세요.** 이 저장소의 `.gitignore` 도 설정 파일을 제외합니다.

제외 기준을 새로 추가하면 그 뒤 실행부터 적용됩니다. 이미 끝난 실행의 순위는 바뀌지 않으므로, 필요하면 해당 버티컬을 다시 돌립니다.

### Claude 데스크탑 채팅, claude.ai (간이판)

일반 채팅에서는 여러 에이전트를 동시에 띄울 수 없어, AI 하나가 같은 절차를 순서대로 진행하는 **간이판 스킬**을 따로 둡니다.

1. [`dist/vertical-research-lite.zip`](dist/vertical-research-lite.zip)을 내려받습니다.
2. **설정 → 기능(Capabilities) → Skills** 에서 zip 을 올립니다. 코드 실행 기능이 켜져 있어야 합니다.
3. 채팅에 설정 파일을 올리고 "북미 건설현장 출입통제 버티컬 업체 조사해 줘"처럼 요청합니다.

간이판은 병렬 조사가 없고 검증도 같은 AI 가 하므로, 플러그인보다 느리고 덜 엄격합니다.

## 자주 묻는 질문

**Q. AI 가 매긴 점수를 믿을 수 있나요?**
AI 는 등급과 근거만 정하고, 검증 에이전트가 출처를 다시 엽니다. 근거가 없으면 0점입니다. 그래도 최종 판단은 사람이 합니다. 검토 표시가 붙은 업체부터 보세요.

**Q. 통신사나 대형 유통사는 왜 후보에서 빠지나요?**
사내 개발팀이 있어도 본업이 서비스 운영이라, SDK 를 받아 제품을 만들어 파는 주체가 아니기 때문입니다. 그런 회사에 솔루션을 납품하는 SI·솔루션사·제조사가 대신 후보가 됩니다. 이 기준이 맞지 않으면 설정의 해당 `knockout` 항목을 빼면 됩니다.

**Q. VMS 업체는 왜 후보에서 빠지나요?**
VMS 나 보안 SW 만 파는 업체는 엔진을 올릴 자기 장비가 없어 엔진 공급으로 이어지기 어렵습니다. 카메라·AI Box·단말기를 직접 만드는 업체를 우선합니다. VMS 플러그인 판매처를 찾는 조사라면 설정에서 `외부 엔진 탑재 제품 없음` 항목을 빼고 돌리면 됩니다.

**Q. 얼굴 엔진을 가진 업체는 모두 빠지나요?**
아니요. 얼굴 검출(Detection)만 자체로 하는 업체는 남깁니다. 얼굴을 비교·식별하는 Matching 까지 자체 엔진으로 하는 업체만 뺍니다.

**Q. 개인 정보를 수집하나요?**
아니요. 담당자는 직책(예: Head of Product)과 그 직책을 확인한 공개 페이지 주소까지만 남깁니다.

**Q. 사내 자료가 외부로 나가지 않나요?**
검색어에는 설정의 `public_terms` 와 일반 산업 용어만 씁니다. `confidential` 항목과 제품 사양 원문은 검색어나 외부 요청에 넣지 않도록 규칙으로 막았습니다. 그래도 회사의 AI 사용 정책은 꼭 확인하세요.
